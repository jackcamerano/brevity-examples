# Deno PR #34903: feat(ext/crypto) implement SubtleCrypto.supports() static method

_Source: https://github.com/denoland/deno/pull/34903_

## Summary

Adds [`SubtleCrypto.supports()`](https://wicg.github.io/webcrypto-modern-algos/#dom-subtlecrypto-supports): synchronous feature detection for Web Crypto algorithm/operation combinations, per the WICG ["Modern Algorithms in the Web Cryptography API"](https://wicg.github.io/webcrypto-modern-algos/) proposal.

Completes the WICG API surface around the PQC and modern-algorithm work landed in #34417 (ChaCha20-Poly1305, SHAKE, cSHAKE, TurboSHAKE, SHA-3), #34447 (ML-KEM), #34448 (ML-DSA). Unlocks progressive enhancement: callers can check before reaching for the new APIs.

```js
if (
  SubtleCrypto.supports("encapsulateKey", "ML-KEM-768", {
    name: "AES-GCM",
    length: 256,
  })
) {
  // … use the WICG ML-KEM KEM-to-KEM flow
}
if (SubtleCrypto.supports("sign", "ML-DSA-65")) {
  // … use post-quantum signing
}
```

Refs #30900.

## What lands

- **`SubtleCrypto.supports(operation, algorithm, lengthOrHash?)`** static method on the `SubtleCrypto` constructor, accepting the 17 operations defined by the spec: \`encrypt\`, \`decrypt\`, \`sign\`, \`verify\`, \`digest\`, \`generateKey\`, \`deriveKey\`, \`deriveBits\`, \`importKey\`, \`exportKey\`, \`wrapKey\`, \`unwrapKey\`, \`encapsulateKey\`, \`encapsulateBits\`, \`decapsulateKey\`, \`decapsulateBits\`, \`getPublicKey\`.
- Overload dispatch on the third argument: number is the bit length (relevant for \`deriveBits\`); object/string is the related algorithm (the derived-key algorithm for \`deriveKey\`, the wrapped/unwrapped key algorithm for \`wrapKey\`/\`unwrapKey\`, or the shared-key algorithm for \`encapsulateKey\`/\`decapsulateKey\`).
- Operation aliasing per the spec sub-algorithm: \`encapsulateKey\`/\`encapsulateBits\` → \`encapsulate\`, \`decapsulateKey\`/\`decapsulateBits\` → \`decapsulate\`, and \`wrapKey\`/\`unwrapKey\` fall back to \`encrypt\`/\`decrypt\` registrations (so e.g. AES-GCM and RSA-OAEP report support for wrap/unwrap).
- \`getPublicKey\` returns \`true\` only for the algorithms whose private \`CryptoKey\` carries enough material for \`CryptoKey.getPublicKey()\` to recover the public key (currently \`ML-DSA-{44,65,87}\` and \`ML-KEM-{512,768,1024}\`).

## Implementation notes

The "check support for an algorithm" sub-algorithm checks the algorithm name against the registered-algorithm tables directly rather than reusing \`normalizeAlgorithm\`, because the spec explicitly requires \`supports()\` to return \`true\` even when operation-specific parameters (e.g. an \`iv\` for AES-GCM) are not supplied:

> Step 6: Execute algorithm operation steps; return true if any step generates a key, returns a value, or lacks required parameters (key, plaintext, ciphertext).

For \`deriveKey\` with a target algorithm we normalize the target via \`get key length\` to compute the bit length for the \`deriveBits\` check.

New tests in \`tests/unit/webcrypto_test.ts\` covering:

- [x] Basic algorithm/operation pairs across digest/encrypt/decrypt/sign/verify/import/export.

- [x] Length overload.
- [x] Missing-args \`TypeError\` from \`webidl.requiredArguments\`.
- [x] Smoke-tested end to end against a debug build.
